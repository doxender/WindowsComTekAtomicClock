# ComTek Atomic Clock — bug-audit pass (2026-06-14)

Read pass over the full source (`src/`, ~7,100 lines of C#) prompted by the v1.1.7
DWM-composition crash report, in the same spirit as the ACS review. Method: read each
source file, trace data flow, flag defects by severity. The **already-fixed** DWM modal
(v1.1.7) is excluded from the list below.

**Severity:** S1 = severe (crash / wrong system time / data loss on the main path) ·
S2 = moderate (security/correctness on a real path) · S3 = minor (hardening, edge-case,
maintainability with a correctness edge).

## Headline

This codebase is in **good shape** — modern .NET 8, clean MVVM, careful atomic-write and
forward-compat patterns, thorough comments. **No S1s.** The two S2s both sit on the
clock-setting path and are partly known-deferred (the §2.5 confirmation flow). Everything
else is S3 hardening. (For contrast: the 20-year-old ACS C++ produced 70 findings including
10 S1.) Count here: **2 S2, 8 S3.**

---

## Service — time sync (highest stakes: this path sets the system clock)

**N1 — S2 — SNTP response has no request/response binding (spoofing resistance).**
`Sync/NtpPacket.cs:62–106` — `ParseResponse` deliberately trusts the local `t1` over the
server's echo (good, for the math), but it never *validates* the response's Originate
Timestamp (bytes 24–31) against the `t1` we sent. The transmitted T1 is a natural nonce;
not checking it means any well-formed SNTP datagram delivered to the socket is accepted as
the answer. Mitigated in practice by `QueryServerAsync`'s **connected** UDP socket
(`SyncWorker.cs:188`), which makes the OS drop datagrams not from the queried peer — so this
is defense-in-depth, not an open door. Still, a clock-setting service should bind
request↔response: reject the response unless its Originate Timestamp ≈ `t1`.

**SW1 — S2 — Clock adjustment is unbounded; the large-offset guard only logs.**
`Sync/SyncWorker.cs:113–136` — on a successful query the worker does
`SetSystemTime(UtcNow + offset)` immediately. The `LargeOffsetThresholdSeconds` check
(line 131) only chooses a log level — it never *gates* the apply. So any offset, including a
bogus multi-year jump from a malicious/compromised server or a spoofed response (see N1), is
written to the system clock at once. The confirmation/clamp flow is explicitly unimplemented
(the §2.5 TODO at the top of the file). Recommend a hard sanity clamp (reject offsets beyond
a sane ceiling, e.g. hours, absent explicit confirmation) independent of the toast flow.

**N2 — S3 — NTP era-0 (2036) rollover.**
`Sync/NtpPacket.cs:121–127` — `ReadNtpTimestamp` treats the 32-bit seconds field as seconds
since 1900 with no era handling; after 2036-02-07 the field wraps and timestamps parse to
~1900. A decade out, but on a clock-setting tool it's a real future correctness issue.

## Service — IPC (privilege boundary: the service runs as LocalSystem)

**IPC1 — S3 — Serial accept loop + no per-client idle timeout (local DoS).**
`Ipc/IpcServer.cs:40–115` — the loop serves one client to completion before accepting the
next, and `HandleConnectionAsync` awaits `ReadAsync` with no idle timeout. A local user
(Interactive Users have ReadWrite on the pipe) who connects and holds the pipe open without
sending blocks the loop, so the real UI can't get status — despite
`maxNumberOfServerInstances: 4` implying concurrency. Low impact (status display only),
local-only. *Context:* all current handlers are read-only, so the IPC attack surface is
small today; it grows when the `SyncNow` / `ConfirmLargeOffset` write paths land.

## Shared — persistence / config

**SS1 — S3 — `WriteAtomic` uses a fixed `.tmp` filename.**
`Settings/SettingsStore.cs:202–217` — the tmp sibling is always `path + ".tmp"`. Two
concurrent writers to the same file (e.g. the UI and a future service-side writer of
`service.json`) would both write that one tmp, interleaving before the `Move`. Single-writer
reality makes it latent; a unique (GUID/PID) tmp name removes the foot-gun. (The atomic-write
pattern itself — flush-then-rename — is otherwise correct and crash-safe.)

**SM1 — S3 — Config-default drift + duplication across the two files.**
`Settings/SettingsModel.cs:233` vs `:318` — `GlobalSettings.SyncInterval` defaults to **1 h**
while `ServiceConfig.SyncInterval` defaults to **12 h**. On a fresh install, before the UI
pushes config, the service syncs every 12 h while the UI's model says 1 h. More broadly, five
settings (`SyncServer`, `TimeSource`, `SyncInterval`, `ConfirmLargeSyncCorrections`,
`LargeOffsetThresholdSeconds`) are duplicated across `settings.json` and `service.json` and
kept in lockstep only by the dialog's Save handler — a standing drift risk.

## ServiceInstaller — privilege design (creates the SYSTEM service)

**SI1 — S3 — `%ProgramData%\ComTekAtomicClock\` is Authenticated-Users-Modify.**
`ServiceInstaller/Program.cs:250–271` — the dir holding `service.json` (read by the
LocalSystem service) is granted AU **Modify** with inheritance. Any authenticated user can
thus influence the SYSTEM time-service's config and create/delete files in that dir. The worst
case is mitigated: `SyncServer` is validated against the published pool via `IsKnownHost`
(`SyncWorker.cs:95`), so it can't be redirected to an arbitrary NTP host. But `SyncInterval`,
`LargeOffsetThresholdSeconds`, and `EventLogSource` are unvalidated user-influenceable inputs
to a SYSTEM process. Consider AU = Read (with a dedicated elevated writer), or validate every
`service.json` field on the service side.

**SI2 — S3 — Service SDDL grants Authenticated Users START/STOP.**
`ServiceInstaller/Program.cs:296–300` — by design, so the unprivileged UI can manage the
service without UAC. Notably AU is **not** granted `SERVICE_CHANGE_CONFIG` (no `DC`), so the
classic "rewrite binPath → SYSTEM RCE" path is closed — good. Residual: any user can stop the
sync (minor DoS) or trigger a privileged clock-set on demand. Acceptable; noted for awareness.

## UI

**VM1 — S3 — `OpenInNewWindow` loses the tab on restart (inconsistent with `NewClockWindow`).**
`ViewModels/MainWindowViewModel.cs:563–601` — moving an existing tab to a floating window does
`Tabs.Remove(vm)`, which (via `OnTabsCollectionChanged`) removes it from `_settings.Tabs` and
persists — but the floating tab is never re-added, so that clock vanishes on restart. The
sibling `NewClockWindow` path explicitly *does* persist its tab. (Floating-window position
persistence is a noted Phase-2 TODO; the bug is the inconsistency where one path keeps the
clock and the other drops it.)

**VM2 — S3 — Latent async re-entrancy on the shared `_ipcClient`.**
`ViewModels/MainWindowViewModel.cs:194–238` — the 1 Hz timer fires `TryFetchLastSyncAsync`
every 5th tick as fire-and-forget. If a fetch ever exceeds the 5 s interval, a second
concurrent invocation can race on `_ipcClient` (e.g. dispose-while-in-use). Unlikely given the
1.5 s connect timeout and fast local IPC, but there's no in-flight guard.

---

## Disposition

None of these are shipping blockers. Suggested order if/when addressed:
1. **SW1** (clamp the offset) and **N1** (validate the originate nonce) — both cheap, both
   harden the one path with real consequence (the system clock). Could ship as a v1.1.8.
2. The S3 cluster as polish: SM1 (align the two SyncInterval defaults) and VM1 (persist the
   moved tab) are the most user-visible.

The 2026-06-14 test project (`src/ComTekAtomicClock.Tests`, 35 tests) now covers the
NtpPacket / TimeSourcePool / IpcWireFormat logic referenced above, so fixes to N1/N2/SW1 can
be landed test-first.
